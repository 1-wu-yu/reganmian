5.

Position：位置，即 x、y、z 三个平移坐标
Orientation：姿态（朝向），机体相对世界坐标系转了多少，通常用四元数表示。
Odometry：里程计，是"位置 + 姿态 + 线速度/角速度"的完整运动状态包，还带坐标系和时间戳。

11. 为什么 ROS 与 PX4 之间需要处理坐标系？

同一位姿在不同坐标系下数字完全不同：VINS 输出在它自己的 world/相机系，PX4 的本地位置是 FRD（x 前、y 右、z 下）机体和本地系。相机装在机身上还有安装旋转和平移（我的外参矩阵含 0.12m、0.08m 的安装偏移和轴置换）。不做变换直接送，飞控会把"相机看到的前方"理解错方向。所以桥脚本必须做坐标系、四元数约定（ENU/NED）和时间戳对齐。

12. 如果 VINS 的坐标方向接反，飞行会出现什么问题？

飞控的位置闭环是"负反馈"：偏东就往西修。方向一旦反了，修正也反了，变成正反馈——飞机往东偏，控制器以为要继续往东修，越推越远，表现为一进 POSCTL/一给位置输入就猛地朝某个方向加速冲出去、瞬间发散甚至翻机。所以接桥后我先在悬停、GPS 兜底状态下观察位置是否跟真势一致，确认方向无误才敢摘 GPS。

13. 如果 VINS 漂移，Position 模式可能出现什么现象？

VINS 给的位置慢慢偏离真实位置，EKF2 信了它，就会控制飞机去"追"一个错误的目标点：飞机实际没动，却以为自己偏了，于是缓慢地向一侧飘走，松杆也停不住；悬停时位置曲线出现单边斜坡而不是水平直线，悬停偏差超 0.5m。这种慢漂比重启更危险，因为它不会立即报错。

14. 

外部视觉更新停止后，EKF2 只能靠 IMU 硬扛，误差迅速累积；超过设定的失效超时后，飞控会按丢失保护策略动作。实际操作中也经常遇到，所以我通过AI把数据链/遥控丢失动作类参数（`NAV_DLL_ACT` 等）设成安全值，并一直保留应急手段：视觉异常立刻把 mask 改回 25 恢复 GPS 兜底，必要时`commander mode auto.land` 。

15. Gazebo Ground Truth 为什么不能直接作为本任务的 PX4 位置输入？

Ground Truth / Model State 是仿真器"开了上帝视角"直接给出的真实位姿，现实飞机上根本不存在这个传感器——它绕过了"传感器→状态估计"整条链路。任务验收的是 VINS-Fusion 能否真正从相机+IMU 估出可用位姿，直接喂真值等于抄答案：VINS 没工作也算成功。所以必须走`/vins_estimator/odometry` →`vision_pose` 这条真实估计链路。

16. 仿真复现成功为什么不代表实机一定可以直接成功？

仿真太"干净"：相机无镜头光晕/运动模糊/曝光变化，IMU 噪声和漂移按模型给，时间戳由仿真`/clock` 统一，天气和光照恒定。实机上有标定误差、相机与 IMU 时间不同步、振动、光照纹理变化、磁场干扰、电池压降等。我在仿真里就吃过时间戳的亏——`/clock` 停滞导致相机多帧同戳，引发 VINS 双重释放崩溃和初始化失败（最后靠丢帧守卫、空队列保护和 endFrame 差一修复才解决），实机这类时序问题只会更多。所以仿真成功只证明算法链路和工程部署正确，实机还要重新标定、同步时间戳、按真实噪声调参。
